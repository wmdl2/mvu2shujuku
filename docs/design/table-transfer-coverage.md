# 聊天副本的覆盖进度适配

自 v0.8.7 起，转换新副本时适配数据库现有聊天格式，复用已公开的数据库接口。原聊天文件保留。

## 数据与进度分别处理

- 已有表的历史记录在新副本沿用。表名唯一、列顺序与DDL相同，并能绑定原持久身份时，重绑新模板至原表key/uid；通过公开聊天模板协调接口更新模板，既有数据库日志不自行重放或改写。
- 整套结构不相容时，内容复用状态导入的字段与表格筛选。额外表按持久身份或唯一名称核对进度，即使列不相容也可以保留来源已经覆盖的楼层。发生多对一匹配时报告歧义。预检分别说明表格内容和进度。
- 映射MVU表的最新状态覆盖迁移前的全部AI楼。额外表保留来源的完成前沿；例如源纪要覆盖12楼、另一表未曾填过，迁移后分别保持12／0。只在新副本最终保存写入原生 `lastImportBaselineAiFloor`，由数据库决定后续计划。

## 文件格式适配

`src/chat-transfer.js:tableCoverage` 读取来源 V2 载体已有的完成事件、检查点进度和导入基线，按数据库的完成前沿计算覆盖楼层。`coverImportedTables` 接收已完成导入的JSONL副本，按实际目标楼与表身份设置基线。若目标楼已有对应full或sheet_full检查点，只合并其进度摘要；否则为当前单表快照建立原生sheet_full/rebase检查点，定位在该楼已有日志之后。日志顺序、隔离槽、表名唯一性和实际存档协议结构均验证。

启用条件是所需来源接口和实际V2存档结构，不使用数据库发行版本白名单。实机基线为1.3.5，不能将验收版本范围当作代码支持范围。未知存档格式不猜测写法，预检保留未自动恢复覆盖的说明。聊天复制走正常新聊天保存、完整导出核对和重开。独立状态导入只暂存当前目标槽的覆盖字段，保存失败先比较并撤回本次字段修改，再回退数据；不因旧运行时值与初始值相同就跳过持久恢复。之后仍由数据库负责回放、调度与正常写入。

这不是通用的数据库编辑器，也不修改原聊天或用户任意历史楼。独立状态JSON仍为v1，没有新增来源逐表历史协议；状态文件导入为映射MVU表建立目标楼基线，额外表沿用目标进度，不能声称迁入了来源额外表历史。零层逻辑存档不按物理楼数猜测，预检拒绝。

## 验证入口

公开回归：`test/chat-transfer.js`、`test/chat-transfer-host-unit.js`、`test/chat-transfer-host-case.js`。

原生数据库集成诊断使用固定85ebff源码和插件实际适配函数：20／12／0、禁用宽容回退的严格回放、后续持久写入、调度器在第20楼不重填并只计划新第21楼，以及压缩采用的进度汇总。诊断不是完整真实模型质量测试。最终实机结果见相应日期验收记录。

冷切卡可能出现原生回放数据已保存、运行时仍旧的情况。插件先核实原生只读回放和候选一致，再复用既有 restoreTableAsJson 同步运行时；此恢复不新增历史日志。对象比较使用现有Lodash深比较，数组顺序和值／类型仍严格区分。
