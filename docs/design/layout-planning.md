# 布局规划与写入边界

本文描述v0.8.2 的精细布局；已发布 v0.8.1 曾将每个映射根变量完整保存为 JSON，旧卡和旧聊天继续按原布局读写，不自动改表。

## 结构判定

布局依据实际执行得到的 Zod 结构、原 MVU 元数据及初始数据，按当前节点判断，复杂后代不使稳定祖先整体退回 JSON。

- 固定结构中的稳定标量保留普通列，纯固定标量对象可逐层展开；number 使用 REAL，明确 integer 才使用 INTEGER。
- 必填且稳定的字典使用行表。固定路径下的字典可成为独立子表，同名集合按完整原路径区分。
- 行记录内的数组、动态字典保留局部 JSON，随所属记录删除，不生成需要模型额外同步删除的关系子表。
- 可缺失／可空容器、数组、未知变换输出、开放固定对象及混合隐藏字段在其所属节点保留完整 JSON。可缺失根的空单元格、JSON null、{}、[] 分别保留缺失、空值和空容器。
- 旧式 `[值, 说明]` 只在该叶子保留 JSON；启用既有 VWD 元数据能力的组沿用完整容器路径。内部 `$` 值随对象保存，发送时按原格式化规则递归过滤。
- 显式开放根整体保存在一张 JSON 表，不另建动态兜底表。没有新增辅助记录或独立结构存档。

普通记录未单独展开的字段由“扩展数据”承接。作者规则保留，不按自然语言猜测字段由谁维护，也不把展示隐藏视为数据库硬写锁。声明中的默认值不证明未校验脚本一定保留字段。

## 原行为与明确取舍

原 MVU 模型更新拒绝删除 required 字段；Zod 的必填、可选与默认行为由原 Schema 执行。删除字典最后一条记录通常留下 `{}`。

原 `Mvu.replaceMvuData` 直接调用酒馆助手 `replaceVariables`，允许绕过登记 Schema 的完整替换。因此，必填约束不能保证作者脚本永不删除整个变量。

用户已确认采用精细布局，并接受以下边界：完整替换若无法无损映射为当前布局，拒绝本次写入，返回失败并保留原数据。不能将这类调用一概称为原卡错误，也不能静默把缺失补成空对象或模板初值。可由 JSON 表达的缺失／空值仍可正常写入。

写入器先在内存草稿执行产品实际 writer，再由实际 codec 读回，与目标状态核对结构和类型；通过后才调用宿主。开场候选、当前回复批次与公共差量入口共用该实现。拒绝结果带明确原因；运行时不把结构拒绝当临时加载失败反复重试。该保护不替代宿主的 SQL 权限或模型遵守表格协议。

## 数据与说明

保留原逻辑路径、数组顺序、重复值、字面键和对象归属。隐藏值和完整初值不复制进 DDL DEFAULT 或示例。说明保留必要定位、编码、SQL 操作与作者原文，不额外生成完整 Schema 清单。未知变换输出不按样本猜成数值列。

## 验证边界

公开回归通过实际转换、writer、codec、状态导出及无 Node 外部作用域的浏览器工厂检查。真实 SQLite 场景检查独立字典、局部 JSON、记录删除、拒绝写入、快照恢复和刷新。开发卡初始读回只证明结构完整性，不等于穷尽剧情或真实模型质量。旧布局回归使用冻结元数据与当前产品实现，不依赖被忽略的旧源码。
