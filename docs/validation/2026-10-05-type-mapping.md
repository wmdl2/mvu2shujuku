# v0.5.1 类型映射验证（2026-10-05）

## 原因与修复

本地 MVU 快照的 `src/variable_def.ts` 将 primitive 类型声明为 string／number／boolean／any；`src/function/schema.ts` 按 JavaScript `typeof` 分类，没有将普通 number 限定为整数。此前转换器自己在多个布局分支将 number 标成 INTEGER。这是转换器的映射错误，SQLite 非 STRICT INTEGER 仍能保存小数不能替代正确的声明。

最终标量类型在声明及规则合并后统一选择：普通 number 使用 REAL；实际 Zod 整数格式、整数倍数约束或 YAML integer 使用 INTEGER；布尔使用 INTEGER 0/1；字符串及 JSON 使用 TEXT。整数元数据来自实际 Zod 对象，不用初值是否为整数推断。JSON 列的物理 TEXT 不受其他组同名数字提示改变。

无 Schema 的嵌套数组还存在可复现的数据损失：混合数组的文字、布尔和 null 被套用数字类型，纯布尔数组读成字符串。现在嵌套／关系数组复用动态标量记录的类型选择和实际 JSON 标量写入协议；混合、未知或可空元素完整保留类型。

## 范围与存档边界

普通 `z.number().min(0).max(5)` 可在数值列生成范围 CHECK。任意 transform 的输出结构继续使用完整 JSON，不试算函数来猜 SQL 类型。`z.coerce.number().transform(v=>_.clamp(v,0,5))` 的评分可以是 3.75，输入 8.25 会由原 Schema 截为 5；其 JSON 列没有 SQL 0–5 CHECK。运行时先执行原 Schema，再通过生产 writer 写回结果。

SQLite 的 INTEGER 列声明本身也不强制拒绝小数；实际整数校验仍由原 Schema 完成。已有聊天不自动迁移列或布局，旧 INTEGER 数值布局仍可读写小数，新映射须重新转换卡和模板。
