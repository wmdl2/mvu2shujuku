## 旧布局导入、声明隐藏字段与开局等待（同日续验）

用户提供的原 MVU 状态档案导入 converter 0.4.0 的旧转换卡时，目标没有可用 Schema。旧实现把当前动态记录键当成声明，再因缺少 Schema 否定其它字段，产生“可导入字段：无”。实际 writer／codec 能无损保存整个状态：现先验证完整候选，只有失败才筛选兼容字段；不运行作者 transform，也不采用源规则覆盖目标规则。没有 statStorage 策略的旧卡必须保留完整输入，不能按新策略提前剥离 `$`。

预览准备期间，宿主延迟写入聊天元数据也会改变快照。仅在预览出现前、同一消息内有限重试准备，最多三次；确认后任何过期仍中止，不自动覆盖。这与放宽并发保护不同。

已核对本地上游：酒馆助手 `src/function/macro_like.ts:getWithout$` 的默认格式化显示递归过滤 `$`；MVU `src/function/update_variables.ts:jsonPatchPathToCommandPath/extractJsonPatch` 不因该前缀禁止更新。隐藏当前值不能推断字段只由脚本维护。用户批准按结构修正：新转换 version 3 的 Schema／InitVar 声明 `$` 根组保留数据库写入位置，发送时隐藏当前值，作者更新要求保留；只有未映射动态脚本根留在原消息。version 1／2 沿用原合同，旧模板不会自动迁移，需要重新转换采用新布局。源样本重新转换生成9表，包含声明 `$` 表；作者更新要求保留、物理写入列可见、发送查询隐藏行，没有推断为只读。

根 JSON 业务规则直接保留作者原文；普通 JSON 在一段规则开头标一次所属列和非空内部路径。保留作者路径、类型、范围和只读文字，不逐行重复生成定位前缀。SQL JSON 路径 `$` 仍表示 SQLite 根节点，与隐藏字段名前缀不是同一概念。

旧布局首楼的多项非初始化写入此前逐个调用 CRUD，各自持久保存。现复用现有当前回复批量提交，不另建写入协议；单项与初始化路径仍保持原行为，批量拒绝不会回退为部分写入。
