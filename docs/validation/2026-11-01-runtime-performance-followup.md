# 运行时性能复查（2026-11-01，未发布）

承接[第一阶段历史准备优化](2026-11-01-history-preparation-performance.md)。第一阶段只减少局部重复，没有解决普通发送中的主要重建；本记录区分实际插件修改、需要宿主接口的候选收益和仍未解决的成本。没有提交、推送或发布，也没有修改用户日常酒馆。

## 插件侧已落盘

1. 消除历史缓存到公开变量接口之间的一次重复完整复制：内部历史读取允许将最终复制交给真实变量 API；作者得到的仍是独立副本。EJS 等其他入口默认保留原复制，swipe 数字参数不会误触发内部延迟复制。
2. 历史准备的有效数据检查改为一次前向扫描，保留无帧楼层继承和请求顺序。1500 消息尚无帧时只检查1500层，不再为每一层回扫前缀；也覆盖首帧很晚和损坏 JSON 存储字段。
3. 候选来源接口适配：宿主提供协议版本1的 `getTableHistoryContext()` 时，缓存按聊天／角色／群组／活动隔离标识辨别来源，不再因普通当前表格对象重新发布就清空旧楼缓存。旧宿主、接口异常或未知协议仍用保守运行时守卫。**该宿主 getter 尚未发布；不能把原型收益算作当前数据库1.3.3已经具有的能力。**

没有改作者提示词、变量布局、存档格式或 SQL 填表协议。首次准备、深层修改、swipe、切聊天、布局和异步过期保护保留；未知 EJS 仍保守预热历史。

## 测量方法与版本

固定 ST1.18.0／TH4.11.3／EJS1.17.9，数据库原版1.3.3（bb2f221d）与两个明确标记的隔离诊断副本。最终插件 index SHA-256：`12c49f2ea16da40e7ddf622f23f3817587b113d90154d1197267808c7479dcea`。工作树含此前未发布的 Schema 与前端修改，不是原样0.8.4标签。

发送对照从同一34消息副本开始：17表、899行，使用本地正文／填表替身，无真实模型服务。填表并发上限3，实际可能有4或5次填表请求，不能用不同轮次计算严格整体速度倍率。浏览器为Chromium153.0.8010.12。模型替身返回无变化SQL，写入正确性另用公开真实SQL场景验证。

读取对照比较相同完整状态：本地MVU实现的 `getMvuData` 直接委派酒馆助手 `getVariables`，基线因此使用真实原生TH函数；它不是完整MVU游戏／额外模型生成性能。每种范围各读取100次；原生基线临时写入同一内存变量快照，同一调用内恢复，不保存私有输入。这个对照只说明数据读取额外成本。

## 结果

| 相同状态的热读取 | 优化前转换卡中位数 | 最终插件＋原版数据库 | 配对原生TH中位数 |
| --- | --- | --- | --- |
| 当前楼，约191KB | 约1.3–1.7ms | 1.6ms | 0.5ms |
| 历史楼，约174KB | 约4–5ms | 0.9ms | 0.2ms |

单次额外成本已降至毫秒量级，不能说比原生读取更快，也不外推为所有布局或设备的上限。

发送中的快照数是多次调用累计申请的楼层边界，包含重复和不同修订，不是聊天存在几百个不同状态。第一阶段曾测得275份；最终插件配原版数据库本轮仍为224份、13次调用，说明仅靠插件局部优化仍不能解决大头。来源接口原型显著减少了整体失效，早期复测与最终冻结包均为8份、5次调用。最终两轮累计接口耗时分别为19350.8ms与4470.7ms，但请求轮次不同且计时包含重叠，不作为总等待时间或严格提速倍率；两轮最长Long Task仍分别达843ms与945ms。

来源原型中需要重读的旧层并非全是浪费：前后文件显示31和33楼的实际 `storageFrame` 修订发生变化，必须按依赖重读其后的状态，不能强行限定“每轮只读两个新楼”。

写入使用公开合成卡，分别执行4次有效变更并恢复原值，按实际完成契约计时。TH基线显式等待聊天保存；数据库API和适配接口已等待其提交保存，不再额外重复保存以虚增适配耗时。

| 写入及保存完成 | 原版数据库等待行为 | 仅诊断移除固定等待 |
| --- | --- | --- |
| 原生TH基线 | 约110–125ms | 约110–121ms |
| 直接数据库SQL | 约969–999ms | 约159–192ms |
| 插件MVU适配写入 | 约1113–1144ms | 约315–332ms |

根因之一是宿主 `refreshMergedDataAndNotifyWithUI_ACU` 在发出通知后默认固定等待800ms。内部已经有 `awaitFrontendReadback=false`，公开写入API没有透传。诊断包仅把该常量改为0来隔离影响，通知、严格提交、保存和其余代码保持。**诊断本身不代表正式能力；参数透传现已在[PR#67](https://github.com/AlbusKen/shujuku/pull/67)实现并验证，尚未合并，当前正式1.3.3仍未提供该公开选项。** 插件150ms合并窗口保留，不提前报告保存成功。 固定等待也可能影响实际界面：若调用者在写入Promise返回后才关闭弹窗、重读数据或渲染，通知先发并不能让这些步骤提前执行。因此不能整体判定该选项影响小；其价值与减少历史回放的CPU成本不同。

转换另测[公开17组×53条记录夹具](../benchmarks/fixtures/runtime-performance-card.js)，使用浏览器生产异步入口，得到17表、901行并完整读回一致。三次转换为493／270／205ms，产物JSON序列化约2–3ms；卡JSON约344KB、模板约116KB。此合成样本未见数秒转换异常，不代表PNG编码、所有远程Schema或全部角色卡耗时。

## 正确性与候选状态

- 最终产品回归：1030通过、0失败。包含来源稳定、隔离切换、接口异常／未知版本、在途拒绝、复制隔离、无帧继承和线性扫描。
- 源码／根构建在验收中冻结，独立构建逐字节核对；原始私卡与聊天不变。
- 33个原始宿主历史快照摘要与同输入基线逐层相同。
- 真实SQLite公开场景：旧楼12.5、22.75与当前44.25分别正确，Mvu／TH／EJS／消息变量读取一致；实际修改、脚本根数据、只读不改表、保存重开通过。固定等待诊断副本也通过对应场景。
- 来源getter草案在独立源码覆盖副本中通过原历史API及新增测试，共31项，类型检查通过。参考数据库保持只读；已提交[来源接口PR#66](https://github.com/AlbusKen/shujuku/pull/66)，尚未合并。

两个宿主方案已获授权并分别提交：[只读来源身份#66](https://github.com/AlbusKen/shujuku/pull/66)、[可选回读等待#67](https://github.com/AlbusKen/shujuku/pull/67)，均尚未合并。第一项31个相关测试，第二项151个相关测试及类型检查通过，保持原默认行为；原生与SQLite分支、执行分派、等待提交、通知／保存、失败及恢复路径均有覆盖。它们分别帮助外部缓存和需要自行调度前端的调用者，不是数据库本体必须调用的新流程。未重新运行整卡或上游完整发布构建，插件正式接入仍需按最终合并接口核对。

## 仍有的成本

来源原型仍有较长主线程任务，采样还看到宿主ScopedConfig复制／旧配置合并及垃圾回收；不能把几百份快照减少等同于所有卡顿消失。插件不应为此删除用户模板归档或直接修改宿主私有配置。历史接口冷回放、首次加载和复杂Schema也可能有真实成本。

本轮没有承诺所有场景快于原MVU，未测真实提供商质量或Android性能。当前结论是：插件侧可安全避免的复制和扫描已处理；主要重复回放及固定等待已有明确、通用的宿主方案，是否采用须完成接口确认和正式验收。


## 2026-11-02 插件写入规划补充（未发布）

`planStatDiffToDb` 原先为并发检查序列化完整表格后，又为草稿序列化一次。现在复用 `beforeJson` 解析独立草稿，公开草稿入口仍自行复制输入。宿主 API、物理类型、楼层选择、写入原子性、提交前并发检查和失败语义不变。此次仅改变内存规划，不改提示词或存档结构。

新增回归检查完整输入仅序列化一次、基线与输入一致、更新结果正确，以及未登记表的草稿也不共享可变引用。相关21项通过。约3.15MB的合成完整表格、空布局、预热8次后交替采样40次，规划阶段中位数由18.86ms降为9.80ms；这是局部 CPU 测量，不包含宿主写库／保存／通知，不代表整次对话性能或真实卡总体收益。

当前回复多步提交仍保留整表原子导入。它不能直接换成任意SQL批次：必须同时证明目标消息、物理行号、类型、原子失败与历史回放等价；本轮没有实施该替换。两个上游PR在本次核对时仍未合并。

配置复制热点属于数据库内部。复核已有发送采样，`cloneScopedConfigData_ACU` 自身累计采样时间分别为1844.4ms（原版宿主）和1987.3ms（来源接口诊断宿主），不是单次复制耗时。原实现对配置做 `JSON.parse(JSON.stringify(value))`；应从读取／合并配置的调用链减少不必要的完整复制，而非在插件中删除模板归档。仍未对外发布此问题。
