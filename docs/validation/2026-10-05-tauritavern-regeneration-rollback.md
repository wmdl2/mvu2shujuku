## 外部脚本与原生操作的关系

| 脚本模式 | 实际动作 | 是否等同于菜单重新生成 |
| --- | --- | --- |
| 原生重生成（默认单击） | 点击 `#option_regenerate`；按钮不存在时尝试文字匹配，再回退 `ctx.generate('regenerate')` | 单角色普通聊天走同一宿主逻辑；脚本不自行删除、不直接改数据库 |
| 全流程重Roll（默认双击） | 尾部为用户楼时删一楼；尾部为 AI 时通过宿主 `deleteLastMessage` 依次删 AI 与用户楼，回填缓存文本，1300ms 后点发送 | 不等同；重新执行用户发送及发送前剧情推进 |
| 回填修改（默认长按） | 同上删除并回填，但不自动发送 | 不等同 |

用户已确认使用“原生重生成”。因此，全流程的 1300ms 等待和助手 `deleteChatMessages` 的事件遗漏都不是该操作的直接路径。按键配置可更改，不能仅根据单击/双击推断模式。

脚本“规划后拦截”是另一个开关，默认关闭，主要在全流程模式中部署：它依据请求 URL、缓存输入及若干硬编码提示词片段识别请求，调用停止生成，增强模式还拒绝 fetch Promise。这不能被当作数据库事务回滚；本次未验证开启后的最新版数据库完整推进管线。

## 原生重新生成的实际时序

TT 单角色普通 `GenerateInternal('regenerate')` 先发 GENERATION_STARTED / GENERATION_AFTER_COMMANDS，随后删除尾部 AI 回复；`deleteMessage` 先 splice，再发 MESSAGE_DELETED。生成流程等待事件监听函数返回，但数据库监听函数只安排延迟任务，立即返回。

数据库 `scheduleChatMutationRefresh_ACU` 在事件停止后等待 1200ms，连续事件的最大等待为 3000ms；任务开始后才恢复丢失 checkpoint、重建 SQLite provider（如启用）、重新合并表格并通知 UI。任务本身还可能等待事务锁和 I/O。

本插件在删除事件取消已有待写任务，并安排回放后前端同步；它没有为宿主生成建立“数据库已回退”的等待屏障。完整旧运行时表格在回放前仍被读侧采用。组件观察中：原回复金币 42，删除后立即读仍为 42；模拟数据库完成回放并发布后读为 10。后者的回放 I/O 为替身，不能作为最新版数据库完整回退验收。

原版 SillyTavern 的对应重新生成分支也先删尾部 AI 并等待 MESSAGE_DELETED，而数据库监听依然采用延迟调度。这是共享的调度风险，不能只归因于 TT 或本转换插件。是否真的在回放前构造请求、是否有脚本保存旧值，取决于实际生成速度和卡内逻辑。

## 核实的边界与风险

| 条件 | 核实结果 | 与用户原生重生成的关系 |
| --- | --- | --- |
| 删除普通 log-only 回复 | 守卫不复活该楼增量，不修改幸存根；本插件已排队的来源失效写入会取消 | 正常对照；早前完整宿主回退证据仍见楼层归属验证，不能扩大为当前新版 TT 验收 |
| 删除后、回放完成前读取或再次保存 | 旧完整运行时仍可读，生成没有等待回放的屏障；额外写入可能把旧状态带入幸存/新楼 | 与本次原生路径相关的时序风险；只读短暂旧值不等于永久不回退，未复现用户那次持久错误 |
| 删除承载唯一 full checkpoint 的楼层 | 数据库守卫优先嫁接到后继；无后继时落到最后一个幸存 AI 楼，可能保留被删快照的数据并清空已被该快照吸收的更早 logs | 保存回放根的有意保护，不是任意历史回滚。旧压缩历史或特殊恢复/初始化边界需要区分；普通增量删除不走这条保值路径。最新版已关闭按普通运行期阈值自动生成 full checkpoint |
| 删除后的防抖窗口中先完成一次数据库保存 | post-save 会按剩余 chat 重建 vault，丢失 checkpoint 的影子副本可能先被丢弃 | 生产守卫与调度器组合验证了此条件；保存完成时刻为夹具指定，不证明手机或某张卡必然触发。上游源码也明确记录该残余竞态 |
| 删除后 1200ms 内又换 swipe | 调度器仅保存最后 reason，删除原因可被 swipe 覆盖，本轮跳过丢失 checkpoint 恢复但仍刷新表格 | 需要同时发生混合事件；单独原生重生成未证明会自动产生该 swipe |
| 使用助手 `deleteChatMessages`，refresh 为静态 none/affected 或 managed affected | 删除与保存/重画路径未发 MESSAGE_DELETED，依赖此事件的数据库回放可能未调度 | 其他卡脚本的风险；用户 V2 脚本用宿主 deleteLastMessage，不走该接口 |
| 全流程模式固定 1300ms 后发送 | 不等于回放完成；模拟慢刷新时发送先于回放结束 | 仅其他模式的风险；不是用户已确认的原生模式 |

SQLite 重建失败后，调度器仍尝试刷新合并数据；这只证明失败隔离，不能据此断言 UI 必然读取旧值或 native/SQLite 已一致。失败保存的 checkpoint 嫁接会撤回对幸存楼的改动；不同 isolation 的根分别处理。
