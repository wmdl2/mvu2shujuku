# 3.2 MVU 卡转换检查（2026-10-05）

本文件记录 v0.4.10 的未修复基线；后续修复与当前限制见 [v0.4.11 验证](2026-10-05-card-api-compatibility.md)。

当前 v0.4.10 默认双模式转换不能视为完整兼容这张卡。已确认四处兼容缺口；其中结构解析失败是转换器缺陷，另外三处是尚未覆盖的引擎、创角写入和外部世界书约定。这些问题的成立不依赖 TauriTavern，但正式安卓应用中的具体表现仍未验收。本轮只分析，没有修改原卡、插件运行代码或发布版本。

受检输入是用户指定的 `3.2_MVU.png`，卡名“缄默之秋3.2 MVU”；输入 SHA-256 为 `da9980e8252c0388108c6477210cd63696f9d05ef81261a6d0c45c539ef12df8`。用真实 `parseCard → convert` 生成 36 张表，目标数据库版本设为 `naiv1.2.4`。参考酒馆助手 4.11.3，Schema 对照使用其依赖的 Zod 4.4.3；这些是审查版本，不代表用户手机实际安装身份。

| 问题 | 已验证行为 | 影响及归因 |
| --- | --- | --- |
| Zod 结构登记未识别 | 完整脚本 `parseRegisteredZodSchema` 返回 null；实际 Zod 可以登记、解析同一 Schema | 转换器扫描正则字面量时误算括号，吞掉后续 Schema 声明；不等于原卡 Schema 无效 |
| 分叉 MVU 引擎仍启用 | 转换后原引擎 import 与数据桥同时保留；执行实际引擎发布函数会覆盖现有父窗口 Mvu | 引擎识别列表漏掉此分叉。旧消息变量与数据库接口可能争用，完整启动时序未在手机复现 |
| 创角最终档案未进入数据库 | 原创角代码通过 `createChatMessages({data:…})` 写消息变量；真实助手实现加组件宿主读回确认未建立相应数据库帧 | 编码内嵌创角流程未适配旧变量写入协议；不能保证最终选择和属性已落表 |
| 配置助手识别旧世界书名 | 绑定转换后的书时，实际解析函数仍选择原名；原书存在、不存在两种对照均如此 | 转换重命名与外部硬编码别名不匹配；自动切换可能找不到书，或作用于旧书 |

Zod 解析问题已有不依赖私有卡的最小复现。下面第一句检查为 true，第二句为 false；它证明前置函数里的正则可以阻断后面的合法 Schema：

```js
const core = require('./src/mvu2shujuku');
const schema = 'const Schema=z.object({enabled:z.boolean().default(false)});registerMvuSchema(Schema);';
const prelude = String.raw`const normalize = (value) => {
  const text = value.replace(/[（(]\s*tag\s*[)）]/gu, '');
  return text;
};`;
console.log(!!core.parseRegisteredZodSchema(schema));
console.log(!!core.parseRegisteredZodSchema(prelude + schema));
```

入口是 `src/schema-layout.js:parseRegisteredZodSchema` 内的 `readInitializerEnd`。这张卡的前置归一函数导致扫描器跳过 Schema；单独取出真实 Schema 声明后能识别根对象，但仍不表示任意辅助函数和 transform 都已等价迁移。

实际 Zod 对初始化补出的“无定义角色模式、扩展内容、生理追踪、超事件、势力发展”五组没有进入转换布局。使用真实表格写入器写入归一结果，返回 `ok: true`、计划 63 次修改，读回却缺少这五组。实际创角快照在所测扩展开关组合下另有八组不入表：无定义角色模式、扩展内容、超事件、生理追踪、业火记录、亚空间、图谱库、金手指；其写入同样返回成功。这是新增根组不能持久化的直接证据，不是根据警告数量推断。

业务约束也存在差异。测试将 SPECIAL 的 E/L 设为 5/4，并写入生命上限 1、当前生命 999。原 Schema 算出生命上限及当前值均为 125、士气上限 120；转换后的真实写入器读回 1/999/null。再把原 Zod 脚本和其实际注册工具加载到组装后的插件运行时，真实 `Mvu.parseMessage` 仍得到 1/999/null。运行时将旧 `*_for_zod` 生命周期参数隔离为副本，保留 Zod 脚本不能据此补回数据库缺失的约束。此对照只证明所测约束未等价，不声称所有原卡规则都失效。

原引擎路径是 `NLKASHEI/MagVarUpdate@e046515/artifact/bundle.js`。当前 `src/mvu2shujuku.js:isMvuEngineScriptContent` 识别主仓库和另一种 offline 发布物，未识别这个分叉。[固定版本的引擎源码](https://raw.githubusercontent.com/NLKASHEI/MagVarUpdate/e046515/artifact/bundle.js) 中，发布函数在 should_enable 为真时把自己的 API 写入父窗口 Mvu，并读取助手消息变量。函数组件对照确认会替换已有兼容对象；没有执行整套外部引擎，不能由此断言每次都会发生争用。

创角页把业务脚本放入 base64 的 `application/octet-stream`，转换前后载荷逐字节一致。最终提交不是一次兼容层 `replaceMvuData`，而是带完整 `data` 的系统消息创建。助手的 `createChatMessages` 将其保存为 `message.variables[0]`，插件数据库读侧没有自动把该字段导入表格。组件测试将档案生命值设为 123，旧变量确实为 123，数据库表格仍是提交前的 null，档案消息也没有数据库帧。Zod 初始化通知可把兼容视图归一为 100，但不能证明档案值 123 已持久化。创角过程中其他直接写入可能已保存部分字段；本结论针对最终档案整包，未把组件存储替身当作真实数据库持久化验收。

[配置助手 v3.2.6 源码](https://raw.githubusercontent.com/NLKASHEI/233456/v3.2.6/缄默之秋配置小助手.min.js) 的别名列表没有转换后缀。真实转换输出将内嵌书和角色绑定都改为“缄默之秋3.2_数据库”，但其解析函数两种对照均返回“缄默之秋3.2”。这里只验收了选书函数，没有执行手机上的全部世界书写入。修复需处理外部脚本的选书契约，不能仅以模板成功导入判定正常。

已通过的检查同样有明确范围：

- 原 InitVar 的 25 个顶层组与转换模板读回完全一致，没有发现原始初始化值遗漏。
- 物品、NPC、私人通讯、当前活动、任务队列的代表性新增数据可读回一致，包含嵌套 JSON、动态字面键、0/false/null。
- 生成的 PNG 再解析与转换后的卡对象一致；原文件哈希未变。
- 三个前端在转换前后的可执行内联脚本共六份，语法解析诊断均为 0。这不等于完整 DOM 或交互验收。
- 混合正文说明与变量更新规则被保留。报告中的 54 项警告不能当作 54 个缺陷；其中有非结构化说明的保守回退。剩余 JSONPatch 与业务说明也不能直接整条删除。

没有发现这张卡自身使用楼层 EJS 标记，不能自动把此前另一张卡的提示词模板设置建议当作本卡修复。状态栏和外部小游戏仍有动态依赖；小游戏使用未固定的 master，Zod 注册工具也没有固定提交，本轮读取的远端文件只代表取证时内容。未完整运行这些外部脚本，未验收正式安卓 TT、最新数据库的 native/SQLite 完整组合，也没有检验长期游玩与旧聊天迁移。

因此，仅关闭原 MVU 或把这些变量改为完整 JSON 不能视为修复完成。后续需要按结构解析与新增组持久化、业务约束迁移、创角整包写入、引擎发布与世界书定位分别修复，再联合验收；这只是修复范围，不代表本轮已获授权实施或已经完成。

公开最小复现可独立运行；真实卡正文、编码载荷和完整导出结果保留在本地取证目录，不纳入公开仓库。
