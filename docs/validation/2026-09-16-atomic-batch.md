# 当前回复的混合更新批次

转换卡脚本通过 MVU 公共写入接口同时修改金币和背包时，原实现可能先增加道具，再因金币
写入失败留下半份更新。本次把当前回复上需要多次宿主调用的更新合并为一次正式导入。
SP 请求模型、解析 SQL/native 填表指令的路径不变，也不增加模型提示内容或调用次数。

## 范围与执行方式

- 针对普通 MVU 写入已经绑定的最新 AI 回复（非开场），包括本楼已有可靠表格帧的情况。
  新楼无可靠帧、消息更新和开场初始化继续使用各自已有的快照路径。
- `createCandidateBuilderFactory` 内的 `createTableDraft` 由开场候选和新批次共用。
  `planCurrentReplyWrites` 让真实 `writeStatDiffToDb` 在隔离内存表中执行一次，记录实际调用，
  包括补行、关联删除、JSON/扩展列以及数组内部导入；没有复制第二套字段规划规则。
- 零调用不写库；恰好一次 CRUD 直接提交，同一行多列仍可合为一次 `updateRow`；两次及以上
  或原本需要导入时，将完整最终表格一次导入。单次 `updateRow` 被拒绝后不降级为逐格写入。
- 规划阶段失败、目标回复失效或原表已变化，均在真实写入前停止。缺少导入能力时拒绝多步
  更新，不先写一部分。保留原有来源守卫及串行队列；重试基于当时的实际数据重新规划。

## 能保证的范围

插件不再把该类混合更新拆成多次独立宿主提交。实际持久化由 SP 的正式提交管线负责；
已经核对的 `table-import-service.ts` 在预检后以完整候选及一次 `data_replace` 提交。
参考版本 `8646e5cc` 与受测 `5c53f795` 的相关导入入口源码一致。

**不能把公开接口返回 false 理解为数据一定未保存。** SP 可能整批持久化成功后，运行时恢复
失败才返回 false。此时不回写旧快照、不改走 CRUD；读取实际数据后重试或确认已经完成。
自动化回归覆盖了“整批已经落库但返回失败”的模拟，未声称实机复现宿主磁盘故障。

旧楼业务补写、直接调用 SP API、监听器自己的外部副作用不在本次批次保证内；多个独立
`replaceMvuData` 调用也不因此成为一个事务。已经进入宿主的调用无法由插件撤销。
VWD、整组可空语义和任意 Zod 执行没有扩展。

## 成本

每批增加隔离内存规划，单次修改也有这项 CPU/复制成本；“保留差量”指最终宿主调用方式。
使用真实 writer 和公开合成数据的本机中位数如下，原始数据见
[测量 JSON](../benchmarks/fixtures/atomic-batch-2026-09-16.json)。

| 行数 | 表格 JSON 大小 | 原有直接差量 | 新单次修改批次 | 新跨表混合批次 |
| --- | ---: | ---: | ---: | ---: |
| 100 | 6,224 字节 | 2.71 ms | 2.31 ms | 2.33 ms |
| 1,000 | 39,526 字节 | 8.83 ms | 10.99 ms | 11.22 ms |
| 10,000 | 399,528 字节 | 50.59 ms | 56.94 ms | 58.45 ms |

Node 22.23.2 / Linux；基准包含本地规划、并发快照比较和内存宿主调用，不含 SP 保存、磁盘、
SQLite hydrate 或回放。100 行的小差异属于测量波动，不据此声称性能提升。跨表多步会改为
整表导入，实际保存开销应另按卡大小观察，不能把本表外推为完整实机延迟。
