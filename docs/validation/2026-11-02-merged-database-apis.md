## 上游与适配

参考库按维护脚本快进到 `85ebff0414a219e5d61a3c0ec5edbafa748e9d1b`，正式产物为数据库 1.3.5。[PR #66](https://github.com/AlbusKen/shujuku/pull/66) 的 `getTableHistoryContext()`、[PR #67](https://github.com/AlbusKen/shujuku/pull/67) 的可选 `awaitFrontendReadback` 已合并；两个接口的正式产物自 1.3.4 提供。[配置复制问题 #68](https://github.com/AlbusKen/shujuku/issues/68) 也已在 1.3.5 修复。本轮没有改动参考库源码。

历史来源接口与此前候选契约一致，`src/message-history.js:historySourceKey` 可以直接使用。仍检查协议版本、聊天／角色／群组／隔离槽身份及真实帧修订；不因当前表格对象重新发布就清空旧楼缓存。接口缺失、异常或协议未知时保留旧宿主的保守回退。

新增 `src/database-write-api.js`，仅为插件自己的会话写入提供局部视图。新宿主的 CRUD 用对象参数附带 `awaitFrontendReadback:false`，整表导入保留原持久化选项并附带该参数；原始 API 对象、默认行为和历史缓存的 API 身份不变。没有来源接口的旧宿主保留原位置参数。该能力组合只用来选择兼容的调用形式；宿主只移植了来源接口而尚未透传等待参数时，额外参数可被忽略，继续原等待。

参数只省略通知后的固定回读窗口，已有提交、保存调用、通知和会话／楼层保护继续执行。原 Promise 的成功或失败继续向上传递，没有提前返回成功。`initGameSession` 等未提供该选项的入口保持原调用。已有转换卡更新扩展及数据库后即可使用，不需要为这两个接口重新转换数据布局。

隔离宿主：SillyTavern 1.18.0（8172dcd）、酒馆助手 4.11.3、提示词模板 1.17.9、数据库 1.3.5。使用公开小型合成卡及本机确定响应服务；流式请求为实际 SSE 分块，不调用远程模型。

- 延迟流式和瞬时非流式生成均成功，旧楼写入完成后再出现 AI 楼，当前值和历史值一致。
- 通过正式 `importTableAsJson(...,{persist:false})` 重新发布同值运行时，确认对象引用改变；来源身份稳定、旧楼值相同，读取旧楼没有新增该楼回放请求。
- 同一构建、同一聊天中，只切换写入等待参数，连续三次实际变更：默认等待共 3843.9ms，关闭额外等待共 945.6ms。每笔返回成功，物理 SQL、公开读取及保存重开值一致。该结果描述串行保存等待，不外推整体游戏耗时或其他卡的倍率。

构建及隔离安装 `index.js` SHA-256 为 `176620a4b04c5d73b7135f694593f99f513f9be0c246605f10b57d241af349f1`。相关 33 项回归通过。完整 1059 项首次运行 1045 通过，14 项因受限环境启动 Python 子进程超时失败；仅在允许子进程的环境补跑这 14 项，全部通过，未修改测试超时或产品实现。

## 原冲突与受控复现

原私卡八轮在旧数据库诊断包中复跑，没有再次触发保存回读冲突，但历史骰盘仍有作者延后写入造成的快照观察差异。不能用乐观读取代替作者队列完成，也不能将这些差异直接算作回读冲突。

原错误日志中两次 `table mutation save readback conflict` 紧接着出现 `Timeout waiting for chat to save`。沿此线索，在公开小卡中保持保存检查逻辑不变，只延迟一次真实保存请求的响应，复现了同类错误：

1. 宿主已有一笔聊天保存，服务器接收的是当时的旧快照，响应暂缓。
2. 接收一笔变量写入，同时由助手追加用户消息并执行 `refresh:'all'`；关闭我们的等待仅用于对照。
3. 酒馆 `saveChatConditional()` 等待已有保存约 1000ms 后超时，记录警告并正常返回；助手随后继续重载聊天。
4. 重载从服务器取回旧快照。数据库提交前记录有 6 楼，回读检查时只有 5 楼，目标楼 `TavernDB_ACU_IsolatedData` 也回到旧值；聊天数组和聊天 ID 都没变。数据库因此拒绝保存完成。
5. 启用已实现的写入衔接后，同一对照的写入返回成功，值保留，没有触发此重载冲突。

一次失败会在异常检查和补偿判断中各调用一次 `fieldsIntact()`，两条诊断记录不能算成两笔失败。上述机制已受控复现，但原来两次没有字段级日志，无法证明它们完全同因。

## 另一个保存确认缺口

去掉助手消息操作，直接调用数据库公开 `updateCell`，也确认了另一个问题：宿主保存忙时，数据库调用保存函数并等到它正常返回，内存帧也没变化，于是返回 true；服务器文件仍可能是旧值。受控测试将 33 改为 34，公开接口返回 true、当前值为 34，重开后为 33。保持数据库默认前端等待的独立对照也得到相同结果，不能将此缺口归因于本轮关闭额外等待。

这是宿主保存超时不抛错与数据库未确认真实保存共同形成的边界。普通 CRUD 走 `saveChatToHost_ACU()` 的尽力保存分支，另一条 `saveChatToHostStrict_ACU()` 默认也未打开服务器回读；仅等待 Promise 或仅验证内存私有字段无法识别“没有真正保存”。这不由 Schema、表格拆分或 SQL 数值类型引起。

隔离试验复用了数据库现有 `saveChatToHostStrict_ACU({verify:true,verifyFields})`，让实际持久化分支回读本次改动的字段。相同直接 CRUD 场景改为返回 false，当前与重开值均保留 33。前一次仅改严格分支的试验未覆盖普通 CRUD，已作为不足方案保留，不能算修复成功。

这只是上游方案验证，未成为插件功能或数据库正式修复。它会增加聊天读取请求，实际范围、性能及失败重试策略需要单独审定；本轮不擅自给插件添加存档、固定等待或服务器回读。正式 1.3.5 仍存在这一慢保存边界，不将 API 返回 true 扩大解释为所有环境下的磁盘确认。
