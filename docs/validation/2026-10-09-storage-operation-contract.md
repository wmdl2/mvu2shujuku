# 拆分存储的结构操作契约

状态：以下是拆分存储失败的历史调查与原型。当前已按用户确认实现混合完整对象方案，相关结构回归通过；最新范围见[混合存储验证](2026-10-09-hybrid-storage.md)，不代表十五张卡或完整游玩验收通过。

## 已复现的原因

`test/stat-storage.js` 两项“结构操作契约”使用明确的公共 CRUD 删除语义夹具，以及产品实际 codec 与存储工厂；不是宿主实机。
最初通过公开数组 before/after 交给 writer 的夹具有歧义：重复公开值无法表达删首项还是尾项。现已改为指定行删除并断言保留的 row_id。
修正后两项删除断言仍通过，完整状态重组断言仍失败：隐藏子字段按旧下标拼回，错配或复活元素。
输入是公开内容相同、隐藏内容不同的两个元素；删除任一元素得到同一公开结果，正确的隐藏结果却不同。
所以最终公开快照不是足够的操作信息，不能用值匹配、下标截断或特殊字段名补齐。

对应 MVU 快照 `src/function/update_variables.ts` 的数组删除分支直接在完整 `variables.stat_data` 上调用 `splice`。
它没有递归拆分存储再重组这一步。本产品新增适配必须证明该结构行为等价。
直接 `replaceMvuData` 则委派完整 `replaceVariables`；不能把完整替换变成无条件保留旧隐藏字段。

## 数据库接口证据

本轮参考库 commit `3c5c1ec` 与实际宿主 DB 1.2.6 / `33757c141f6e3df768efc50f7eef372ceaedf50a` 分开记录。
以下接口定位来自参考库，不把它当成已受测宿主的新功能：

- `presentation/bootstrap/api-groups/callback-api.ts`：更新回调给出最新表快照与 `persisted`，不提供执行前扩展入口；填表开始通知也不传操作。
- `presentation/bootstrap/api-groups/sql-api.ts:executeSqlMutation`：先经内部提交执行，再刷新与通知。
- `service/table/update-orchestrator.ts`：统一 SQL 填表直接调用内部提交与 provider，包装公开 SQL API 不能覆盖这一链路。
- `service/table/table-update-commit.ts`：内部存在 `beforePersist`，但在操作执行后，且它不是供所有外部更新统一注册的执行前接口。
- `service/table/sql-table-service.ts:normalizeSqlStatementsForRuntimeLog_ACU`：日志保留规范化 SQL；获取日志不等于可以把任意 SQL 在完整对象上再执行一次。

提交后重放也不能作为通用方案：非确定 SQL 表达式再次执行可能产生不同结果；完整 JSON 替换本来就可能删除隐藏子字段，不能把所有写入都当成局部合并。

### 继续调查后的能力边界

前一轮把“更新通知仅含快照”直接推成需要新增数据库接口，结论过早。V2 frame 还有 `operations` 与 `writeSet`：明确的 `row_delete`、单元格写集、SQL 文本及参数可以提供更多信息。指定行删除可按真实行身份承接，不能将所有操作都归为信息不足。还必须解决隐藏快照对应哪一版表数据及楼层的问题。

但仅凭事后快照和日志仍有已证实的缺口：

- 原生 `updateRow` 只修改传入的列，持久化为最终整行 `row_upsert`，写集为整表。用官方 TypeScript 5.9.3 提取并执行参考库原回调，分别将甲列或乙列的 JSON 替换为各自相同的公开值，得到相同表数据、operation 和 writeSet。两个完整字段替换应删除的隐藏子字段却不同。宿主、提交和保存为替代；这是上游回调级证据，不是实机。源码 SHA-256 `3066d735…`。
- SQL 日志保留语句不保证二次执行相同。使用实际生成的完整 JSON DDL，对 `ORDER BY random()` 的两次调用提供固定的不同合法排序序列；公开元素相同使公开结果仍相同，但隐藏数据排列不同。这是 SQLite 原型，random 为确定夹具替代，不是宿主或模型质量验证。

另一路线已经找到现有入口：SQLite 的 `updateConfig.sendRowsSqlTemplate` 可替代默认发送行数据，之后仍经 EJS 渲染。已提取实际固定 DB1.2.6 构建的 `formatTableForSqliteMode` 执行，结合本仓库实际 EJS 与默认展示过滤：原 JSON 保留隐藏值，发送视图保留公开值而不含隐藏值，原表内容不变。列投影、provider 与 SQL 模板查询为替代，模板不包含查询宏；不代表完整宿主请求验收。受测数据库构建 SHA-256 `4cbf9e83…`。

此入口目前只在 SQLite 分支生效；存在隐藏物理列时该自定义配置会被忽略；自定义分支也不能默认继承原发送行数窗口。因此不能直接用于所有 native/both 场景、混合字段或所有分组。混合容器保持整体还有清空/重填保护与原消息恢复的存储契约需要证明。

这些结果支持优先研究“完整容器存储、发送视图过滤”，而不是默认要求新增执行接口。尚未决定将混合容器移入数据库，也未改变原消息保存方案。

### 完整容器路线的进一步核对

已从实际固定 DB1.2.6 构建提取原生 `parseAndApplyTableEditsToData_ACU` 及其原解析/JSON 清洗函数，在 VM 中执行四项样本：删除首行、删除末行、完整 JSON 字段替换、修改另一列保留 JSON。全部通过。表顺序、无锁配置及非总结表判断为夹具替代，没有运行宿主提交或保存。证据 `native-container-actual-build-proof.json`，构建 SHA-256 仍为 `4cbf9e83…`。这证明原生引擎也能在完整 JSON 上正确执行这些操作，不证明递归拆分方案已修复。

同一实际构建的 `prepareAIInput_ACU` 原生分支直接执行 `visibleColumns.map(...row[sourceIndex]).join(', ')`；函数不读取 `sendRowsSqlTemplate`。完整 JSON 中的 `$` 子字段会随单元格文本进入默认行展示。现有上下文排除规则是起止边界文本删除，不是 JSON 对象投影；条件模板也不是逐单元格 JSON 展示接口。不能用这些配置宣称已覆盖原生模式的安全过滤。

参考库 `update-orchestrator.ts:applyUnifiedGroupFillResponses` 的原生路径在进入 `runTableUpdateCommit_ACU` 前，已经对工作副本调用 `parseAndApplyTableEditsToData_ACU`。因此，即使将中央保存函数的 `beforePersist` 公开，也不足以让全部操作在完整对象上执行。若研究执行扩展，必须位于实际执行之前，覆盖 provider 与原生工作副本，而不是只给保存路径增加回调。

主动清空/重填是数据库新增的维护操作，不能从 MVU 的格式化宏推出它应保留哪些混合记录。需要区分：

- 独立 `$` 子树仍保存在原消息中时，清空数据库不影响它。
- 若一条公开记录内部包含 `$` 子字段，完整删除这条记录在原 MVU 中也会删除其 `$` 子字段；保留并按位置拼回不是原行为。
- 手动重填先清除旧行，再让模型创建新行。新行不是旧记录的稳定身份；两条公开内容相同的旧记录拥有不同隐藏值时，无法靠名称或位置决定新行继承哪份隐藏值。

所以“完整删除遵循原行为”与“清空重填后任意混合记录的隐藏值自动沿用”不能通过重组算法同时保证。后者需要单独定义维护语义，例如阻止这类容器的破坏性重填，或将重填明确视为新容器；目前没有替用户选择。可证明的原执行行为、默认展示过滤与新增维护策略须分开讨论，不把维护策略说成上游原规则。

### 真实样本与定位依据

继续核对十五张卡 InitVar 与冻结转换卡的 `extensions.mvu2shujuku.statStorage.initial`：一张卡在两个非根对象中同时声明公开字段与 `$` 子字段，冻结隐藏状态共有七个非根 `$` 字段。它的已启用变量列表使用原 `format_message_variable::stat_data` 宏。未发现初始化中的混合隐藏数组；脚本运行后状态与未来作者数据不在此次库存结论内。不能把重复公开值、不同隐藏缓存的构造反例说成这批卡已发生的原文场景。

原 MVU 没有单元格，也没有根据隐藏值配对公开记录的步骤：两类字段本来就是同一个对象的属性，路径或操作时数组下标负责定位。转换布局将容器放进完整 JSON 单元格时，才出现单元格内混合可见性。数组中两条公开值相同的记录仍有不同的操作地址；问题是事后公开快照丢失了该操作地址，不能反推出完整结果。若原作者要求模型依据未展示的信息选择记录，原框架也不能补足该信息。

用户已决定新转换仅支持 SQL，原生发送投影不再属于新转换的实现目标。该决定没有自动批准混合容器移入数据库或阻止重填的维护策略。当前已收敛转换、刷新、模板和界面至 SQLite，旧模式参数报告后生成 SQLite 产物；旧聊天不迁移，不更改宿主全局模式。宿主实际模式/回退检查与混合结构存储问题仍待完成，不能将这项入口收敛当成结构缺口修复。

## 最小执行原型

命令：`node test/stat-storage-execution-probe.js`（Node 22 内置 SQLite）。
八项通过：行表首尾删除、JSON 字段局部修改与完整替换、整列数组首尾删除、重排和整个容器替换。
使用产品生成的实际 DDL，在包含原隐藏子字段的完整候选上执行一次，再调用实际存储工厂分配结果；完整替换按原操作移除被替换内容中的隐藏字段。

这只证明上述 JSON/数组样本的执行顺序可行。原型未接入宿主，未证明普通行表的隐藏非映射字段、任意 SQL、所有约束、原生 DSL、持久化或错误回滚；不能据此声称新增一个回调就完成全部适配。

## 尚未决定的架构方向

候选之一是保持现有模型协议与原消息存储要求，研究数据库正式扩展入口：在统一提交边界提供实际操作及其候选状态，复用原引擎执行一次，在同一提交周期内处理隐藏状态与回滚。必须覆盖自动填表、手动重填、公开 CRUD/SQL 和导入，并证明 JSON 子字段及记录身份能完整承接；单独公开一个提交后通知不够。继续调查后不再把它作为唯一或已必需的方向。

这可能需要提高数据库依赖要求，属于此前“仅在本插件适配”之外的新架构决定；未获用户确认，也未修改参考库或发送上游请求。
另一候选是调整递归拆分策略，例如混合容器保持整体、再解决显示过滤及清空恢复。SQLite 已有部分可利用接口，但仍有上文列出的未验证范围。该方向同样改变已经讨论过的存储约定，不应静默实施。用户最新指示是继续分析，当前不要求立即在前轮两项中选择。

已可独立修正的事项：投影不得提前序列化消除非法 JSON，继续由原 writer 校验；普通数字表不增加 JSON 可写路径标题；回归按当前正常列、动态兜底表定位，同时保留旧布局兼容检查。
原拆分存储的两项失败保持可见，版本仍为 0.8.0 未发布，无提交或推送。
