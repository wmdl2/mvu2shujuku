# 社区语料转换问题的根因与剩余风险

> 本文记录真实执行改造前的诊断。用户随后批准改为实际 JavaScript/Zod 构造，下面三类属性语法缺口已由生产新路径解决；最新架构与验收见[真实 Schema 执行验证](2026-10-05-schema-execution.md)。旧文本解析辅助接口仍有本文所述边界。

日期：2026-10-05。对象为改造前的0.5.0已受测源码；本轮仅分析和小样本复现，未修改产品、构建、版本或逐卡产物。已完成验证见[0.5.0验收](2026-10-05-remote-schema-branches.md)。

15张卡通过转换与所覆盖的源数据写读验证，不代表15张都已完成正常游玩验收。全部私人卡的界面、创角、剧情、自动化及宿主生命周期尚未逐一实机检查。尤其含自带业务引擎、禁用原结构脚本的样本，Schema组件可提取并不证明其业务运行兼容。

## 有MVU源码为何仍有缺陷

转换器按MVU行为实现兼容层，同时将数据存储和更新接入数据库。MVU源码用于核对初始化、路径、命令、事件和变量接口；静态提取作者JavaScript/Zod声明、生成关系表、编解码与数据库保存均是新增实现。MVU并不提供这些实现的正确性保证。

本地MVU资料是无Git元数据的快照，不能宣称对应当前所有卡的分支。Zod工具、作者业务脚本、第三方宿主和数据库也各有自己的版本与语义。不过，本批多处错误确属转换器实现与测试覆盖不足，不能全部归因于作者扩展或版本差异。

| 已遇到的问题 | 根因 | MVU源码本身为何无法防止 |
| --- | --- | --- |
| 跨行／压缩声明、逗号声明、作用域和打包导出提取不完整 | 静态扫描器只识别部分JS语法，并非执行JS得到Schema | MVU直接运行作者脚本，无须推断其文本表达形式 |
| 空InitVar只由Schema默认值初始化、远程Schema遗漏 | 结构来源此前不完整：卡内初值不能代表全部运行时声明 | 默认补齐来自Zod及作者工具，远程模块也不在卡内正文 |
| 其他开场含缺失根组或不同类型 | 固定布局只看部分样本，原运行时可按分支替换整份对象 | MVU会对各swipe单独初始化；转换器还要提前生成可容纳分支的表 |
| 混合字典、联合类型被编码为文本，字符串受同名数字字段污染 | 从样本或不完整路径推断类型；类型与路径绑定错误 | JS对象保留原始值类型，关系表编码需额外保持这些差异 |
| 完整JSON被重复叶子列覆盖；删字段后复活；空父对象语义错误 | 同一路径有多个数据来源，以及缺失/null/空对象的表示不够精确 | 数据库重建对象引入了MVU原对象读取所没有的覆盖与补齐过程 |
| 删行后动态字段写到旧行号 | 删除改变物理位置；数据库导出实际返回克隆快照 | MVU按对象业务路径操作；转换器必须另外协调业务键、物理行号与新快照 |

原MVU初始化代码会逐个swipe解析开场InitVar、替换角色书初值并发初始化事件；更新代码包含命令及Zod专用事件阶段。原外部Zod工具还能逐命令校验、清理命令、处理初始化。当前复用实际Schema守住候选数据的校验和变换；逐命令扩展钩子及任意作者业务的完整行为仍需要单独验证。数据结构相同不能证明所有事件和业务副作用相同。

## 改造前确认的语法缺口

用实际Zod构造Schema，再调用生产 `parseRegisteredZodSchema` 和 `convert` 做对照。所有样本的实际Schema均要求同一个“状态”对象，且其默认值为 `{值: 1}`。普通显式属性作为控制样本通过。

| 合法JS写法 | 实际字段 | 当前提取／转换结果 |
| --- | --- | --- |
| `{"状态": 状态Schema}` | 状态 | 正确 |
| `{"\u72b6\u6001": 状态Schema}` | 状态 | 保留原转义文本作为字段名；默认开局生成错误根组 |
| `{['状态']: 状态Schema}` | 状态 | 把 `['状态']` 整段当字段名；默认开局生成错误根组 |
| `{状态}`（先定义同名Schema变量） | 状态 | 属性被忽略，完整静态默认开局被误拒绝 |

三种异常均没有产生相应 `unsupported` 项。定位在 `src/schema-layout.js:parseRegisteredZodSchema` 的对象成员处理：当前只取冒号前文本并剥离首尾引号，没有解码JS字符串键、解析静态计算属性或处理属性简写。前两项已经经过生产转换器验证，属于错误产物，而不只是推测。

这些公共小样本不证明15张语料卡具有相同问题；此前273表、62输入及双模式宿主证据继续有效。679项回归也不能覆盖尚未加入测试的输入种类。产品指纹仍与0.5.0冻结记录相同。

## 如何减少下一批同类问题

1. 优先修复会悄悄生成错误数据的结构解析，使用语法树识别静态成员、作用域与字面量；仍只分析静态可确定表达式，不执行任意作者代码。无法确定结构时明确保留完整JSON或拒绝，不能把未识别误写成不存在，更不能误判为完整默认值。
2. 对受支持声明做语义对照：等价JS写法应生成同一布局；原Schema归一化后的源对象应与转换器写读结果一致。组合检查缺失/null/空对象、嵌套联合、混合记录、动态字段和批量增删，不只逐个检查单一功能。
3. 继续使用真实数据库的克隆快照及宿主时序，检查删行／写入／保存／重载／切分支／切聊天；测试替身要遵守真实API契约。
4. 要宣称某张卡可以正常玩，逐卡验收其创角、状态栏、实际业务动作、全部开场和保存重载。固定响应只能证明协议，不代表真实模型能正确推进所有剧情。

测试先以原数据为基线。错误初值经过相互匹配的编码器与解码器可以原样往返，因此单纯“生成表格→读回→再写入”会漏掉从源对象到表格时已发生的损失。本批改用原InitVar和各开场输入、实际Schema归一化以及实机克隆快照，正是为了减少这类盲点。

语法树能改善语法覆盖与告警质量，仍不能静态推导任意JS函数、动态依赖和全部业务副作用。当前建议优先补三个已复现缺口，再扩大语义对照和逐卡实机验收，不以增加卡数量代替这些检查。
