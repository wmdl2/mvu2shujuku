# 转换时多聊天迁移验收（2026-11-15）

本功能随 v0.8.6 收尾，按用户本轮要求本地提交；本轮不推送。使用方式见[用户说明](../../README.md#转换时同时迁移聊天)，实现契约见[运行时说明](../runtime.md#转换时复制聊天)。

## 用户决定与实现

来源卡独立选择，支持名称不同及多选聊天；每条来源新建独立目标聊天。沿用现有最新状态迁移，不构造数据库历史帧、不改数据库。每楼只复制当前选中正文，其他候选留在原聊天，旧楼状态不逐楼转换。

字段兼容降级及额外表匹配复用 state-transfer，各聊天独立以目标初值为基线；未知旧世界书绑定不覆盖新卡。只写新聊天，取消不删除已完成副本，已含正文或用户改动的失败副本保留。

## 实际宿主

Node 22.23.2，ST 1.18.0（8172dcd），TH 4.11.3，EJS 1.17.9，龙血玄黄·数据库 1.3.5（85ebff0414a219e5d61a3c0ec5edbafa748e9d1b），实际 SQLite。参考官方 main 获取到 c45d50ee，与受测发布包分开记录。

`test/chat-transfer-host-case.js` 经真实转换／保存按钮分别覆盖普通 MVU 文件源和已有转换卡源。两个场景都迁移两条聊天到名称不同、增加字段的新卡：金币分别保留 37／81，新增魔力沿用目标初值 30；预检明示部分兼容，辅助变量保留，目标只含所选分支。重开后状态保持，正文中旧值 999 的指令未重跑。两场景的原聊天 JSONL 逐字节不变，浏览器异常为零。

发现并修复两项问题：恢复正文时必须保留新聊天中宿主生成的全部载体及原楼号，不能丢弃最新提交依赖的早期基线；原生重新加载替换消息对象后，须在 `CHAT_LOADED` 上登记已有快照的历史指令基线。后者也覆盖普通旧聊天的同类重载路径，不改写旧正文。

所用 MVU 快照的 `initResponse` 监听 `MESSAGE_RECEIVED` 并处理指定消息，聊天切换不扫描执行整段历史；这里的历史基线修复与该行为对齐。

原生夹具使用原 Schema 生成器，先经正常选卡建立目录；聊天上传字段是 `avatar`，角色导入文件名需补 `.png`。脚本／世界书授权使用真实弹窗，并按弹窗内容区分并发预览。专用服务复用后已核验身份关闭。
