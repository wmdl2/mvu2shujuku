# 固定输入的宿主性能归因（2026-11-02）

承接[数据库独立诊断](2026-11-02-database-performance-diagnostics.md)。本轮没有修改产品代码、升级版本或重新发布，也没有因只改诊断脚本重跑产品全量；根产物仍为已通过1033项的 `d78569128ec73f74424ef5432b07007131182829d828cf70b2d6bf7f300c65d0`。

## 条件与统计窗口

隔离ST1.18.0（8172dcd）、数据库1.3.3（bb2f221d）、酒馆助手4.11.3、提示词模板1.17.9，Node22.23.2与Playwright Chromium。受测卡使用公开17表×53行夹具，共901行、21条固定消息；归档负载取自此前本机受测聊天，只读取原文件，配置约2.88MB，未把私卡正文或归档内容公开。

所有作者脚本在各组中都关闭，测试只调用数据库和公开EJS接口，不以脚本失败减少工作量。复制计数器只加入隔离数据库副本，两个模式共用同一计数器；记录调用数及函数内累计时间，不在每次复制中额外序列化计量大小。表格初始完整读回与公开夹具一致，实际SQLite查询确认每张示例表53行。

第一层对照只切换兼容层的激活标记，扩展仍加载，静态提示适配保留；因此测到的是兼容层激活带来的增量，不能当作卸载扩展后的所有差异。第二层另外在浏览器中完全禁用本扩展，确认核心全局未加载，用于验证数据库本身的复制成本。

来源接口诊断包与原版脚本逐字节比较，差异只有插入的275字节 `getTableHistoryContext`；其他数据库代码相同。它是既有[PR#66](https://github.com/AlbusKen/shujuku/pull/66)的隔离原型，不是已发布能力。EJS事件和作者执行流程保持，未加入跳过上下文回调的快捷路径。

## 请求准备与普通EJS文本

每个条件采样3次。每次先以同样数据重新发布运行时对象，持久帧没有变化；历史缓存已经预热。这用于隔离“运行时对象换了但历史没变”的失效成本，不包含首次冷准备。请求准备真实触发酒馆的CHAT_COMPLETION_SETTINGS_READY事件，输入为20个固定普通文本块；EJS项调用真实公开evalTemplate且文本没有模板标记。两者均不调用模型。

| 数据库／兼容层 | 20文本请求准备中位数 | 配置复制次数 | 普通EJS文本中位数 | 配置复制次数 |
| --- | ---: | ---: | ---: | ---: |
| 原版、未激活兼容层 | 142.7ms | 21 | 0.9ms | 0 |
| 原版、激活兼容层 | 214.7ms | 23 | 70.4ms | 2 |
| 来源原型、未激活兼容层 | 150.6ms | 21 | 0.9ms | 0 |
| 来源原型、激活兼容层 | 142.9ms | 21 | 1.1ms | 0 |

原版活跃路径在每个上述处理阶段额外读取20个历史边界；来源原型保持已有缓存后为0。各轮输出、表格数据一致，计时阶段console错误和历史API失败均为0。小样本耗时有运行噪声，不能把原型活跃项比未激活项少几毫秒写成提速；调用数量的差异是更直接的归因证据。

原因：EJS公开evalTemplate会先prepareContext，再由内部eval判断是否有模板标记。转换器在prepare事件上为未知作者代码保守准备历史；旧宿主在运行时重新发布后又无法证明来源未换，因而重读。来源getter使原缓存保护可以区分来源，不需要改变EJS事件覆盖或猜测作者代码。

## 正常增量填表

使用公开triggerUpdate的真实提交路径，不用会清空表的手动重建。固定一个分组，使用本机拦截的合法UPDATE固定响应；每轮必须恰好一次请求并公开报告success。每种兼容层状态各2次，初始聊天帧、数据和配置先还原，历史预热在计时之外。各组表格内容保持一致，阶段错误及历史API失败均为0。

| 数据库／兼容层 | 每轮模型请求 | 配置复制次数 | 额外历史边界申请 |
| --- | ---: | ---: | ---: |
| 原版、未激活兼容层 | 1 | 45 | 0 |
| 原版、激活兼容层 | 1 | 49 | 40（两次各20） |
| 来源原型、未激活兼容层 | 1 | 45 | 0 |
| 来源原型、激活兼容层 | 1 | 45 | 0 |

每个数据库包内部的4轮模型请求哈希完全相同，排除了此前4／5次请求不同的问题；两个包新建角色的名称不同，跨包不计算严格速度倍率。原版未激活项的配置复制中位数约288ms、活跃项约307ms。API返回均约1.3秒，未单独拆分保存、异步刷新等等待。此前在公开CRUD／导入路径确认的800ms不能直接套入本次triggerUpdate；不把API总时间当CPU，也不把少量总时延差当作稳定收益。

完全不加载扩展的补充基线仍有45次配置复制，累计约286～293ms，实际SQLite、API成功反馈、一次请求及表格内容检查通过。这独立确认正常数据库流程本身会产生该成本。

但完全卸载组的最终请求与适配组并非逐字节相同：8条消息中仅第3条的适配说明位置及边界换行不同，其余消息与请求字段相同。这是现有说明前置行为。严格哈希校验拒绝了这组总耗时比较；未修改提示词来强行通过，也不把卸载组用于全流程速度比。

最初的增量填表夹具错误使用SELECT固定响应，被数据库作为非法填表语法拒绝并重试；该批计时已丢弃。triggerUpdate在该版本返回结果对象，完成条件以success字段为准。最终有效组均为合法UPDATE、成功且每轮一次请求。

## 结论与限制

数据库自身的完整配置复制与插件触发的额外历史准备都是真实来源。约两秒的旧混合采样不能全归给任何一方；本轮没有反推旧测试的调用次数。数据库共有的重复复制由[issue#68](https://github.com/AlbusKen/shujuku/issues/68)跟踪，插件这组额外回放可由既有只读来源接口方案消除。两个接口PR在本轮回读时仍open，未合并。

这些是固定处理阶段和单组增量填表对照，不是完整原卡游戏、网络提供商质量或所有历史编辑方式的验收。首次冷回放、真实旧帧变更及任意作者EJS仍有必要成本。启动期间有被网络围栏阻止的资源加载及世界书准备警告，不在计时阶段；本轮不将其作为整卡可玩性通过结论。
