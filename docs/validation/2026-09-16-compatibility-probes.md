# 动态说明与原 Schema 复用能力探针

状态：2026-09-16 完成定向探针；**没有开启 VWD，没有修改产品源码或默认行为**。
这是对候选架构的验证，不是新增功能验收，也没有重做已完成的综合审查。

后续 VWD 动态渲染已经实施，最新范围与验证见[动态说明验收](2026-09-16-vwd-prompt.md)；
本页保留探针当时的结论。原 MVU 更新模式与 Zod 宿主接口按用户决定暂缓。

## 结论

| 候选 | 已验证 | 尚不能承诺 |
| --- | --- | --- |
| 说明存为隐藏数据，实际请求时展开 | 两种存储模式的主 API、SQLite 独立 API均读到当前说明；刷新保留、删楼回退 | 任意说明文本原样保留；整套 VWD 的值/说明协调写入；历史批量填表上下文 |
| 直接复用作者 Zod 辅助脚本与 Schema 对象 | 原命令处理、拒绝非法值、类型转换，以及真实表格 codec 往返 | 整批 SQL 校验与原逐命令语义相同；所有作者脚本均可直接保留 |
| 使用 SP 表格更新回调做提交前校验 | 实机回调收到 `persisted: true`，返回 false 后数据仍保留并可刷新读回 | 该回调可否决提交；不能依赖修改回调数据来模拟前置校验 |

因此“不能更新 note，所以 VWD 只能等上游”过于绝对。当前静态方案的限制可以绕开，
但动态渲染还需要文本保护和完整生命周期验收。Schema 对象本身可复用，主要缺口在写入协议
与校验时机；不能把它归为“数据库不能执行 Zod”。

## 动态说明实验

公开合成卡在 `状态表` 保存隐藏字段 `$动态说明`，初始为“说明甲”。变量规则中的固定 note
包含 EJS 读取表达式与 SP 自带的 `{[db.表.where(...).get(...)]}` 查询表达式。
这些只是能力探针，**没有生成实验 VWD 布局，也没有启用说明写入守卫之外的通道**。

- SQLite 和 native：实际填表请求依次看到“说明甲”→写入“说明乙”→刷新后“说明乙”→删楼后
  “说明甲”，全程 note 原文保持不变。隐藏列不作为普通业务列暴露。
- SQLite 的 SP 查询表达式同样生效；native 保留原表达式，不能把它用作双模式统一方案。
- SQLite 独立 API 也能读取“说明丙”。请求体的 model 为 `isolated-direct-probe`，主 API 为
  `isolated-fixture`；没有把主 API 请求误记成独立 API。
- SP 在 `prompt-api-call.ts` 中先调用 `EjsTemplate.evalTemplate`、替换 SQL 查询表达式，
  随后才分流主 API/独立 API。上游仍可能在后续阶段继续处理模板。

**字面文本探针发现限制：** 说明设为
`字面量 <%= 40 + 2 %>；查询 {[db.状态表.where("row_id",1).get("金币")]}；末尾`，
其在 EJS 说明位置的实际请求为：

| 请求路径 | 实际说明文本 |
| --- | --- |
| 主 API | `字面量 42；查询 37；末尾` |
| SP 独立 API | `字面量 <%= 40 + 2 %>；查询 37；末尾` |

这项实验成功复现了文本不保真的问题，**不算“任意文本安全通过”**。不能直接把动态值拼进
EJS 后就开启 VWD；HTML/JSON 转义也不能未经实际管线验证就当作解决所有模板语法的办法。

### 建议的实施方向

1. 沿用现有实验布局的字段身份、隐藏覆盖数据、默认说明和逐字段插槽计划；表格仍是唯一
   持久化来源，note 变成固定渲染入口，不在每次说明变化时改写模板。
2. 一次渲染读取一个一致快照并填入全部说明，避免每个字段都重新重建完整 `stat_data`。
   静态默认、显式空串、同文不同字段和非法元数据回退继续沿用已有契约。
3. **先处理文本保真再接通写入。** 优先找所有模板处理完成后的文本插入入口；若没有稳定
   入口，就验证针对该管线的转义/占位恢复方案。限制说明文本范围只能作为明确的部分支持，
   不能静默改文或宣称完整 VWD。不要包装全局 fetch 来修补所有请求。
4. 能力缺失、模板执行失败、换卡/换楼和历史填表上下文不明时不能“说明已保存但继续发旧说明”。
   需要把这些失败边界连同值/说明同批更新、刷新、删楼、初始空说明及原有开场路径一起验收。
5. 首批仍限已有实验范围的单例 pair/jsonPairOptional；不顺带扩展动态行、数字/布尔 pair、
   任意对象或迁移旧聊天。完成前保持 `vwdExperimental` 关闭。

该路线不需要新增模型调用，也不需要向模型额外发送内部元数据。正式渲染器尚未实施，
没有测量其 CPU/内存成本；此次固定响应实验不证明真实模型填表质量或 token 节省比例。

## 原 Schema 复用实验

使用[作者原始 mvu_zod.ts](https://github.com/StageDog/tavern_resource/blob/main/util/mvu_zod.ts)
的注册与命令处理代码，Zod 4.6.5；仅在 Node 探针内去除 TS 类型、模块导出并替换错误文本
格式化导入。事件总线、UI 通知和注册宿主为替身，Schema 和原命令算法是真实实现。
JSON 克隆与命令值解析替身仅覆盖本探针使用的 JSON 数据，不代表任意 YAML 或对象兼容。

原辅助脚本会逐条执行命令并 `safeParse`。受核对的 MVU 源码中，JSONPatch `replace` 会先转为
相应 set 命令，再进入这些事件，因此命令顺序问题也涉及该路径；本探针本身从命令阶段开始，
没有把全文 JSONPatch 解析或完整浏览器 Schema 注册算作已验证。

实测例子：初始生命 100、上限 100，Schema 限制生命不能超过上限。

- 先设置生命 120，再设置上限 150：原脚本逐条处理后生命为 **100**。
- 先形成生命 120、上限 150 的最终对象，再校验一次：生命为 **120**。
- 金币设为 -5 被原 Schema 拒绝，随后生命字符串 `"80"` 转为数字 80，其他值不变。
- 原脚本输出经过产品真正调用的候选工厂与 `statDataFromTables` 往返，结果一致。

所以可以复用作者原函数，而不必静态翻译所有 transform/refine；但简单地在最终 JSON 上调用
一次 `schema.parse` 只能叫“候选对象校验”，不能叫完整复现原 MVU 命令语义。

### 提交入口与取舍

SP 当前公开 `registerTableUpdateCallback` 是更新通知，返回值不参与提交判定，也不会等待
异步回调。源码传出的数据可能是活引用，不要修改它试图撤销提交。实机返回 false 后金币仍从
37 变为 38，刷新仍为 38，回调元数据为 `persisted: true`。

内部 `table-update-commit.ts` 已有异步 `beforePersist`，但没有暴露为插件可注册的候选校验接口。
包装公共 `updateCell/executeSql` 也不能覆盖 SP 内部模型 SQL 调用。

若继续此方向，推荐准备宿主接口建议：在正确会话/楼层内提供 before/candidate、操作来源，
允许等待校验并返回新候选或整批拒绝，再重新验证和一次提交。还需明确 SQL CHECK 与 Schema
修正的先后顺序；若 SQL 已先拒绝越界值，后置钩子无法再执行原本会成功的 clamp。
这是未来方案，本轮没有发布 issue 或修改 SP。

保留原 MVU 命令语义作为另一种更新入口也可研究，但必须选择唯一更新驱动，不能让原 MVU
引擎和 SP 自动填表同时更新。它会扩大产品范围，当前不建议为任意 Zod 自建第二套 SQL 执行器。
整组 nullable 的表示丢失也不会仅因复用 Schema 自动消失，本次不扩展该项。
