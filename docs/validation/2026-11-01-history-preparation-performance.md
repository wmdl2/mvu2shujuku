# 历史准备范围与缓存性能验证（2026-11-01，未发布）

本轮保留既有 Schema 与前端修改，处理历史变量准备范围过大和缓存反复丢弃。没有修改变量结构、作者提示词或存档格式；未提交、推送或发布。运行时修复作用于受测旧转换卡，不要求重新转换模板。

## 实现范围

- 单楼渲染、更新及 swipe 只准备该楼；翻页准备实际挂载消息范围；后台通知与窗口登记优先准备已挂载状态栏。聊天加载仍完整预热。
- 存储变化从最早受影响楼层起失效，保留此前已提交的历史缓存。追加、删尾、共享存储别名和深层原位修改均检查；正文对象更换但数据库输入相同时不重复回放。
- 缓存命中不等待无关冷读取；在途任务跨代后仍拒绝过期结果，不发布半批。内容未变的表更新通知不再主动清空历史缓存，业务事件及提交反馈保留。
- 宏仍由原宿主解析；有效映射完全相同时复用布局身份，变化时仍失效。

涉及 `src/message-history.js` 和 `src/extension-runtime.js` 的历史准备入口、布局解析及更新回调。公开工厂回归在 `test/message-history.js`；`test/mvu-public-api.js` 的前端准备夹具同步新函数签名。

## 性能结果与限制

两轮都在相同输入下重载并预热。重复准备场景将最新消息的存储包装替换成等内容新对象，然后执行同一动态 EJS 六次；它验证后续楼变化是否无谓丢弃已准备前缀，不代表首次冷加载。

| 场景／指标 | 修改前（已修复的数据库） | 最终包 |
| --- | --- | --- |
| 上述六次 EJS 总耗时 | 922.1ms | 16.4ms |
| 上述历史接口调用／快照数 | 1 次／32 份 | 0 次／0 份 |
| 正常发送的历史接口调用 | 13 次 | 14 次 |
| 正常发送申请快照总数（含重复） | 376 份 | 275 份 |
| 正常发送历史接口累计耗时 | 13912.2ms | 14082.1ms |
| 正常发送最长观察 Long Task | 701ms | 627ms |
| 正常发送接口 context_changed | 2 次 | 4 次 |
| 浏览器异常 | 0 | 0 |

累计接口耗时包含重叠调用及被拒绝的读取，不能视为用户等待时间。单次对照不证明整体生成变快或 Long Task 稳定下降。正常发送减少了申请范围，但未测出明显整体耗时改善，不能宣称卡顿已消除。无变化 SQL 的模型替身只验证发送与准备时序，真实持久化另由下面的公开 SQL 场景验证。

诊断显示，样本中已填充缓存的整体失效主要伴随数据库重新发布运行时对象，以及消息存储／长度变化。该样本未把布局重新解析或无变化回调证明为主要原因；它们的修复由公开合同回归支持。

运行时对象更换仍整体失效：受测公开接口没有活动隔离槽／来源版本标识，不能凭数据相等假定同一来源。若要安全地继续减少这些回放，需要宿主提供可验证的来源身份和修订契约。未知作者 EJS 仍能同步选择任意历史楼层，无已知范围时保留全历史准备；不静态猜测依赖、重复执行作者代码或用当前值顶替旧楼值。Android、其他宿主及真实模型质量未在本轮验收。
