# 源码契约与旧问题复核（2026-10-08）

本文记录该阶段结果；后续动态变量与历史读取已接入，当前范围以[变量适配验证](2026-10-08-variable-adapter.md)为准。

本次接续统一填表适配，检查此前被判为无法迁移的内容是否真的恢复行为。版本仍为 0.8.0，改动未发布、未提交。结论是：自然语言和原计算的保留解决了此前静态迁移门控造成的问题，但运行时变量接口还存在独立缺口，不能据此宣称十五张卡全部可正常游玩。

## 从源码划分职责

MVU、酒馆助手和提示词模板承担不同职责。MVU 的 `getMvuData` / `replaceMvuData` 在参考快照中将选项交给酒馆助手的变量接口；世界书里的 `getvar`、`getMessageVar`、`setMessageVar` 则由提示词模板实现。转换器接管这些名称时，须保留对应来源的路径、作用域、消息选择和返回值契约，不能只替换存储位置。

此次遗漏有共同原因：静态字面量改写被当作变量接口接管，简化 helper 没有完整承接上游选项；另外将混合文本直接当 JavaScript 扫描，混淆了两种语法边界。统一填表说明解决的是自然语言规则迁移，不会自动修复这些运行时契约。后续应以源码契约覆盖驱动实现，而不是以样本警告消失作为完成标准。

本轮使用本地 MVU 快照的 `src/function/global/index.ts`、提示词模板 1.17.9（`d6f520d149aba146305b0b781ddd691d449c28d2`）的 `src/function/variables.ts`、`src/function/ejs.ts`、`src/modules/exports.ts`，以及数据库 1.2.6（`33757c141f6e3df768efc50f7eef372ceaedf50a`）的读写接口与存储帧实现。MVU 快照没有 Git 身份，不视为最新上游。

| 契约 | 当前证据与处理 |
| --- | --- |
| EJS 的文本/代码边界 | 修复只在实际执行的 EJS 块中改写；正文引号不再遮蔽后续调用。正文示例、EJS 注释和转义标签保持原文。 |
| 缺失字段与 `defaults` | 修复选项对象被误当成默认值；没有 `defaults` 时仍返回 `undefined`，保留 0、false、null。 |
| Lodash 路径和数组 | EJS getter/setter 复用现有路径解析器，支持下标、带点键和空键；setter 保留已有数组并按数值下标创建新数组，拒绝原型污染路径。 |
| 动态路径 | 静态改写仍只能识别可确认的字面量；变量/拼接形成的路径可能继续写入原生消息变量，没有进入数据库。尚未解决。 |
| 消息/作用域选择 | EJS `withMsg` 以及 MVU `type` / `message_id` 是源码定义的行为。当前兼容 helper 与部分 shim 主要服务当前数据库状态，不能宣称这些选项完整支持。 |
| `index`、`clone` 与写入选项 | `index` 是存储值经 JSON 解码后的数据下标，不是消息编号。`flags`、`results`、`merge`、`dryRun` 也会影响执行及返回值。源码已定位，完整接管尚未实现。 |
| 作者自然语言业务要求 | 原文保留，统一说明要求按当前填表协议输出；不按个别卡的措辞推导并改写业务。 |

这些接口契约应成为覆盖清单；卡样本负责检验覆盖，不能替代接口契约。后续运行时适配应让 JavaScript 自己算出路径，通过统一的变量入口选择存储后端，并复用同一套选项语义。不要继续扩充“某张卡恰好写了什么”的字符串匹配。

### 下一阶段方案（尚未实施）

1. 建立统一变量门面。EJS 的原 API 名称和已有兼容 helper 调用同一实现；JavaScript 先计算实参，再由门面按路径与作用域选择数据库或原生接口。`const p = 'stat_data.' + name; setMessageVar(p, value)` 不再依赖转换器推导 `name`。
2. 根据固定上游源码整理选项、别名及返回值，覆盖缺失、JSON 下标、条件写入、合并、删除、返回旧值、试算与缓存。非数据库变量委托原接口，不无条件重定向全局/本地变量。
3. 为数据库后端区分当前状态与指定消息/swipe 的历史状态。先证明历史读取，再核对历史写入会怎样影响后续存档；不把“不支持历史”悄悄解释为“操作当前楼层”。若后端确实无法表达某项行为，需给出明确能力限制。历史写入支持范围是后续需确认的产品决策，本轮没有自动采用拒绝、降级或修改日志的策略。
4. 公开测试按接口契约组织，角色卡作为补充验收。每种选项检查实际调用、返回值、数据库读回及非目标数据，兼顾原生与实际 SQLite；不要只检查转换文本包含 helper 名称。

统一门面减少表达式写法带来的遗漏，但不意味着无需维护：上游新增 API、作者使用私有内部状态、未知外部脚本，以及目标宿主缺少的能力仍需明确边界。

## 宿主验证与限制

实际宿主使用 SillyTavern 1.18.0、酒馆助手 4.11.3、提示词模板 1.17.9 与上述固定数据库 1.2.6，隔离数据、关闭角色浅加载，不调用模型。此前双模式验证已证明以下产品缺口：

1. 动态路径设置原生消息金币为 73，数据库仍为 42；字面量接管路径可以写入数据库。
2. 历史消息金币为 9，带 `withMsg:{id:0}` 的转换读取却得到当前值 44。
3. 带同一历史选项的转换 setter 把当前数据库写为 49，目标楼层没有被遵循。

这些是兼容层行为遗漏；不能算作上游数据库问题。历史写入还需核对数据库的快照/增量日志与后续楼层关系，直接改变当前表或随意改历史帧都不能保证等价。下一阶段需明确统一入口可支持的历史能力，再实现并验收；本轮没有暗中改变历史读写策略。
